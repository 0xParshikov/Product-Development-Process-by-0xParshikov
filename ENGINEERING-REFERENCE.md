# Справочник производственного процесса

Часть [ENGINEERING.md](ENGINEERING.md). Раздел читается, когда наступил его случай.

## Проект

EPIC-000 проектирует весь проект и проходит сокращённый цикл без Delivery, DoD и Rollout:

**Project Discovery → Project Challenge → DoR проекта → Closure**

Владелец согласует тип работы, истории с критериями и DoR проекта, а после Closure закрывает эпик.

- **Project Discovery** идёт по шагам Discovery, но для проекта целиком: основной агент проектирует систему, Product Owner фиксирует требования в PROJECT.md, а эпики с зависимостями, порядком и оценками — в ROADMAP.md. До ответа владельца по каждой истории проверка проекта не начинается. Документы будущих эпиков не создаются: детали эпика определяются в его Discovery. Дизайн-директор согласует с владельцем дизайн-систему проекта.
- **Project Challenge** проверяет документы по разделу «Проверки ролей»: до трёх циклов, блокеры возвращаются в Project Discovery.
- **DoR проекта.** Product Owner готовит: цель, границы, требования, истории и критерии, дизайн, эпики, зависимости, оценки, риски и открытые вопросы. Ответ **«DoR проекта согласован»** разрешает Closure EPIC-000; реализации будущих эпиков нет.

## После лимита

Когда лимит циклов исчерпан, автономная серия заканчивается.

**Одно исправление перед DoR.** После лимита Project Challenge или Pre-Challenge основной агент может один раз исправить технический пропуск в плане без обращения к владельцу, если согласованные истории, критерии, архитектура, Rollout и принятый риск остаются прежними. Исправление проверяют затронутые роли и Product Owner последним. Повторный или новый блокер завершает серию; число циклов не обнуляется.

**Иначе решает владелец:** останавливает работу, разделяет её либо разрешает новую серию Discovery с изменёнными границами или решением. Перед предложением новой серии основной агент пересматривает затронутое решение целиком и объясняет причину тупика и изменение подхода, начиная с упрощения и переиспользования. Циклы новой серии считаются заново.

## Название чата

Codex меняет название через WebSocket текущего `app-server`: сокет — `~/.codex/app-server-control/app-server-control.sock`, ID задачи — `CODEX_THREAD_ID`. Порядок: `initialize` → `initialized` → `thread/read` → `thread/name/set` → `thread/read`. Существующее название сохраняется, меняется только префикс.

Claude Code меняет название инструментами `claude-code-remote`: ID — из `get_session`, затем `set_session_title`; сохранённое сверяется по его ответу. Без них владелец применяет сообщённое название командой `/rename` и подтверждает.

Создание и архивирование выполняются штатными инструментами. Прямое изменение локальной базы запрещено.

## Документы

| Общий файл в PLATFORM | Назначение | Куратор |
| --- | --- | --- |
| AGENTS.md | Роли и общие правила | CTO |
| ENGINEERING.md, ENGINEERING-REFERENCE.md | Производственный процесс и его справочник | CTO |
| ARCHITECTURE.md | Устройство системы, ограничения размещений и архитектурные принципы; без адресов | Основной агент; CTO проверяет независимо |
| NETWORK.md | Сеть и доступ к сервисам | Главный администратор |
| WORKSPACES.md | Проекты и их рабочие папки | Главный администратор |
| DEPLOYMENTS.json | Единственное место точных адресов, источников и состояния выпусков | Главный администратор |
| RISKS.md | Риски, проверки и решения владельца | CyberSec; CTO — технические риски |
| PROCESS-ISSUES.md | Подтверждённые открытые проблемы производства | CTO |
| TONE-OF-VOICE.md | Правила пользовательского текста | Дизайн-директор |
| DESIGN_UI.md | Правила оформления интерфейса и дизайн-принципы | Дизайн-директор |

RISKS.md: `риск; последствие; устранение; исполнитель; проверка; решение владельца; статус`. CyberSec и CTO предлагают изменения единого списка: не более семи актуальных рисков, включая принятые владельцем. Превышение предъявляется владельцу с предложением устранения; скрывать риски ради лимита запрещено. Риск не остаётся со статусом «не проверен» дольше одного эпика: в Closure CyberSec подтверждает проверку или выносит владельцу решение. Устранённое удаляется после согласования. Номера записей общих реестров не меняются и не переиспользуются.

PROCESS-ISSUES.md: карточка до десяти строк — `факт (дата, проект); причина; правка процесса; проверка; статус`. Повтор — одна строка с датой в той же карточке. Карточка закрывается после принятой правки и трёх работ без повтора.

Локальный AGENTS.md проекта содержит только ссылку на PLATFORM и особенности проекта; общие правила и ПрП не копируются. Другая версия ПрП применяется только по поручению владельца; источник фиксируется на всю инициативу.

**Файлы проекта** хранятся в `projects/<project>/` внутри Платформы либо в папке проекта; отсутствующие создаются по циклу.

- README — работающие возможности и использование.
- PROJECT.md — только действующее, в этом порядке: цель; границы; общие требования; истории с критериями открытых и запланированных работ; действующие решения владельца; блок текущего состояния (до 10 строк); ссылки на документы проектирования и план. Материалы закрытой работы остаются в её папке (эпик — `epics/<номер>/`, задача — файлы Superpowers) и заменяются в PROJECT одной строкой-ссылкой; история — в Git. При чистке сверяются ID историй, критерии и решения владельца: каждый на месте или помечен заменённым.
- ROADMAP.md — связь ID историй с эпиками (сама история целиком — в PROJECT), планируемые результаты, зависимости, порядок, оценки.

README, PROJECT и ROADMAP ведёт Product Owner. Документы проектирования и план пишет основной агент, независимо проверяет CTO. Проектные правки перечисляются в DoR; остальные согласуются отдельно.

Перед интеграцией параллельная ветка сверяет каждый общий и проектный документ с целевой веткой и объединяет только записи и разделы своей инициативы; заменять целый файл устаревшей копией запрещено.

## Выпуск

В согласованной установке, обновлении или снятии агент меняет только записи своего проекта в DEPLOYMENTS.json: `assigned` — размещение назначено; `active` — установленная версия проверена по NETWORK.md; `retired` — снятие проверено. В `last_verified` указываются выполненные проверки и их ограничения; `active` не заменяет приёмку владельца. У записи хранятся только текущий и предыдущий выпуск; история — в Git. Это не разрешает менять ARCHITECTURE.md, NETWORK.md или чужие записи. Прежнее состояние, результаты проверки и откат — в плане текущей работы.

Если Rollout может прервать основного агента, его выполняет штатный независимый механизм целевого контура с сохранением результата. Отдельный управляющий скрипт или сервис создаётся только как согласованная история.
